# Relocation server

For a new dual MID360 Super-LIO map, use
`super_lio_localization/launch/super_lio_mapping.launch.py`. It launches SC and
BTC builders against synchronized `/mapping/keyframe_scan` and
`/mapping/keyframe_odom`, saves `map.pcd`, then builds BBS3D when
`/super_lio_mapper/finalize_map` is called. The mapper waits for both builders'
finalize services before publishing the map directory. See the Super-LIO README
for calibration and launch commands. Set the same absolute `maps_root` for
mapping and runtime map loaders, or set `localization.maps_root` in the launcher
settings. An empty `maps_root` retains the installed `maps_folder` default.

The ROS 2 `relocalizer_service_node` service uses
`localization_msgs/srv/Relocation`. The request contains a local LiDAR cloud,
`map_name`, and `relocation_method`:

| Method | Algorithm | Required directory below `maps_folder/maps/<map_name>` |
| --- | --- | --- |
| `0` | Scan Context retrieval + NDT-OMP | `scancontext` |
| `1` | BTC retrieval + geometric verification + NDT-OMP | `btc` |
| `2` | BBS3D global search | `bbs3d` |

SC and BTC databases can be generated by the ROS 2 builders in this package.
The directory names above are fixed by `RelocationManager`. A successful service response is a pose of the
**query point-cloud frame in the `map` frame**. The historical pose stored in
each database entry must likewise be a pose of its point-cloud frame in the
same `map` frame as `map.pcd`. Historical and query point clouds must use the
same local axis convention and compatible field of view. In particular,
an odometry pose of `base_link` cannot be stored for a cloud in another frame
without applying the corresponding extrinsic transform. The returned pose is computed as
`T_map_query = T_map_history * T_history_query`.

## Database contract

The readers accept the formats written by the AutoInitialize Scan Context and
BTC implementations:

```text
maps/<map_name>/scancontext/
  index.txt             # one .sc path per line
  entries/000000.sc     # pose, original cloud path, ring key, descriptor
  clouds/000000.pcd     # pcl::PointXYZI in historical point-cloud coordinates

maps/<map_name>/btc/
  index.txt             # one .btc path per line
  entries/000000.btc    # BTS1/version 1 descriptor binary, pose, paths
  clouds/000000.pcd     # pcl::PointXYZI in historical point-cloud coordinates
  planes/000000.pcd     # pcl::PointXYZINormal for BTC verification

maps/<map_name>/bbs3d/
  voxelmaps_coords/voxel_params.txt
  voxelmaps_coords/0.pcd ... <max_level>.pcd
```

Index paths may be relative to the database directory. Old absolute paths are
also accepted; when an old path no longer exists, the loader tries an entry
with the same filename under `entries/`. Cloud and plane paths inside each
entry may also be relative to the database directory. Prefer relative paths
for databases that may be installed or moved. Restart the server after
replacing a database at the same path; loaded databases are cached.

The SC descriptor parameters `num_rings`, `num_sectors`, `max_radius`, and
`lidar_height` must equal those used by the database builder. BTC's
`is_high_fly` setting selects its descriptor extraction profile and must
likewise agree with the producer. The original file formats do not record all
of these parameters, so they must be managed alongside the database.

## Building SC and BTC databases from a ROS 2 bag

The builders subscribe to synchronized `sensor_msgs/msg/PointCloud2` and
`nav_msgs/msg/Odometry`. Set `cloud_topic`, `odom_topic`, `map_frame`, and
`output_dir` in `config/sc_builder.yaml` or `config/btc_builder.yaml`, or
override them with ROS 2 parameters. The output directory must be empty.
For example, set `output_dir` to
`mapping/maps_folder/maps/<map_name>/scancontext` or
`mapping/maps_folder/maps/<map_name>/btc` before playing the bag:

```bash
ros2 run relocation_server sc_map_builder --ros-args --params-file \
  /path/to/relocation_server/config/sc_builder.yaml \
  -p output_dir:=/path/to/mapping/maps_folder/maps/my_map/scancontext
ros2 run relocation_server btc_map_builder --ros-args --params-file \
  /path/to/relocation_server/config/btc_builder.yaml \
  -p output_dir:=/path/to/mapping/maps_folder/maps/my_map/btc
ros2 bag play /path/to/bag --clock
```

Run the builders in separate terminals before bag playback. The odometry
header frame must equal `map_frame`, and its pose must describe the frame of
the point cloud. If `child_frame_id` is present, the builders check it against
the point cloud `frame_id`; an empty `child_frame_id` is accepted with a warning
and the same-frame assumption. If odometry describes `base_link` while the
cloud is in another frame, transform the odometry pose into the cloud frame
before building the database. The builders do not apply sensor extrinsics.
The cloud and odometry timestamps must be within `sync_tolerance_sec`.
SC descriptor parameters and BTC `is_high_fly` must match the server settings.
The builders write relative index and cloud paths so the result can be moved.
The server currently reads the installed `maps_folder` share directory; its
map root is fixed in `relocalizer_node.cpp`. After writing a
database into the source tree, rebuild or reinstall `maps_folder` (or copy the
database into the installed map directory) before calling the service.

## Building a BBS3D index

Use the point-cloud map in the same coordinates that the service will return.
The builder accepts a single PCD with finite XYZ points and writes the
hierarchical voxelmaps expected by the loader:

```bash
ros2 run relocation_server bbs3d_map_builder \
  /path/to/mapping/maps_folder/maps/my_map/map.pcd \
  /path/to/mapping/maps_folder/maps/my_map/bbs3d 1.0 6 2
```

The arguments after the output directory are `min_resolution_m`, `max_level`,
and `voxel_expansion_rate`. The output directory must be empty. Resolution and
hierarchy metadata are stored in `voxel_params.txt` and loaded by the server.
The server uses a prebuilt index, so `bbs3d_params.tar_leaf_size` has no effect
on it; downsample the input map before running the builder if needed. The
official 3D-BBS examples recommend a gravity-aligned query scan, limited
roll/pitch search, and a map containing the entire query scene.

## Runtime configuration

The server parameter definitions and defaults are in
`config/relocation_parameters.yaml`. Runtime overrides are in
`config/relocation_settings.yaml`, which the package launch file loads. SC and
BTC share the NDT optimizer parameters. `min_points` applies to both;
`max_fitness` applies to BTC and the legacy SC path. The MSF and RT clients have a `relocation_method` parameter that
defaults to `2`; set it to `0` or `1` and set `relocation_map_name` to select
the corresponding database. The service response uses `success=false` when
loading, retrieval, or refinement fails. Details are written to server logs.

### SC map submap refinement

SC defaults to `sc_params.map_refinement_enable: true`. The loader requires
`map.pcd` alongside `scancontext/`, in the same map frame as the stored poses.
It caches the downsampled map and a bounded LRU of submaps, including their
NDT distributions, ICP targets and verification KD trees. Submaps cover the
entire configured query range plus the allowed translation correction and
cache-cell offset. Switching databases clears submap caches; restart the
server after replacing files at the same path.

Ring-key retrieval retains ten candidates by default. Up to
`sc_params.max_refinement_candidates` seeds are refined in map coordinates
using NDT followed by ICP. Map NDT uses at most 20 iterations (also bounded by
the shared NDT iteration limit) before 20 fine ICP iterations. If NDT only
stopped at its cap, it continues from the ICP-corrected pose using the remaining
shared NDT budget, then repeats ICP and verifies the final result. The prepared
source resolution is retained throughout. Its line-search step
is 0.2 (`map_refinement_params.ndt_step_size`); legacy SC/BTC keep the shared
step setting. The log distinguishes an iteration cap from numerical convergence.
Nearby seeds are skipped only after a representative
passes; a rejected seed does not suppress the remaining seeds at that place.
Height differences above `candidate_merge_height` preserve separate floor
hypotheses. Distinct verified locations with nearly equal geometric scores
are rejected as ambiguous. The SC descriptor threshold remains 0.25.
Competing floors require the larger `floor_ambiguity_score_margin` separation;
a small improvement caused by sampling density must not pick a floor arbitrarily.

`map_refinement_params` controls range, caches, ICP and acceptance. Default
acceptance requires at least 65% of **all prepared query points** to have a
correspondence within 0.75 m, an inlier RMSE at most 0.35 m, and support in at
least 60% of occupied query azimuth sectors. At least four sectors must be
occupied. Translation/rotation corrections are bounded too. These checks use
Euclidean distances (meters); the logged legacy `fitness` is a mean squared
distance and is diagnostic in this path. The thresholds are starting values
verified on the recorded platform/2floors scenes, not a calibrated probability
of a correct pose. Super-LIO still validates the returned candidate separately.

Set `sc_params.map_refinement_enable: false` at startup to restore historical
single-frame NDT and its `ndt_params.max_fitness` check. BTC/BBS3D behavior and
the relocation service interface are unchanged. `SC MAP candidate` logs expose
entry, descriptor distance, overlap, RMSE, sector coverage, cache use, correction,
elapsed time and rejection reason.
The supplied launcher/Super-LIO settings allow 45 seconds for a response, since
multiple difficult seeds can exceed the old 30-second deadline. This is a
client deadline, not cancellation of a running server computation. Manual pose
handling and the separate initialization timeout are retained.

With `BUILD_TESTING=ON`, `test_map_registration` checks geometric false positives,
candidate fallback, ambiguous places, global pose composition and cache/map
switching. `sc_offline_probe` runs the actual SC pipeline on fixed PCD queries:

```bash
build/relocation_server/sc_offline_probe /absolute/maps/my_map \
  /absolute/query_paths.txt /tmp/sc_results.csv
# Append "legacy" to run the historical-frame comparison.
```

The query list contains one absolute PCD path per line. This first change does
not alter moving-scan accumulation or the client's initialization time reference;
those need separate motion-compensated validation.

`config/relocation_settings.yaml` also contains `bbs3d_params`, including
angular search bounds, score threshold, source downsampling, scan range, and
timeout. Select `relocation_method` and `relocation_map_name` in
`localization/multi_localizer/config/msf_localizer_settings.yaml` or
`rt_localizer_settings.yaml`. The server reads the corresponding method
directory below the installed `maps_folder/maps/<map_name>`.

For `bringup_everything.launch.py`, choose the localization backend and relocation
policy in `launcher/config/localization_settings.yaml`. `localization.relocation.mode`
is `auto` or `manual`, and `auto_method` selects `sc`, `btc`, or `bbs3d`. Both MSF and
Super-LIO limit automatic attempts to five by default, including candidate validation;
after failure they wait for RViz `/initialpose`. Manual mode skips this service. Auto
mode launches this service in its own container so global search cannot block MSF's
sensor and manual-pose callbacks. These orchestration options are separate from the
algorithm parameters in this package. A client response timeout does not cancel an
ongoing server computation; expired responses are ignored by the clients.

The Scan Context and BTC core code is derived from `/root/autoinitialize/src/AutoInitialize`
and retains its source package naming to preserve the database format and
algorithm interfaces. Its MIT license is included as `LICENSE.autoinitialize`.
